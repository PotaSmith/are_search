================================================================
AreSearch BulkIndexer 利用ガイド
================================================================

このガイドは、BulkIndexer の準備、実行、再開、recover、結果確認、巨大データを含む新IndexTargetへの切り替えを扱う。
BulkIndexer の内部構造は扱わない。


# 1. 使用前に確認する
================================================================

以下を確認する。

    対象の IndexTarget がモデルに定義されている
    使用する stage が対象 IndexTarget に定義されている
    対象 IndexTarget の Elasticsearch index が作成済み
    実行環境から Elasticsearch とDBへ接続できる
    結果保存先として、削除されない書き込み可能なディレクトリを用意できる

BulkIndexer は対象 IndexTarget の alias が存在しない場合、bulk投入を開始しない。
通常同期や別のbulk実行を自動停止しないため、同時更新を避ける必要がある場合は利用側で停止または排他を行う。


# 2. サンプルを生成する
================================================================

Railsアプリケーションのルートで実行する。

    bin/rails generate are_search:sample

BulkIndexer で使用するサンプル。

    tmp/are_search/sample/are_search_bulk_index.rb.sample
    tmp/are_search/sample/are_search_bulk_index.sh.sample

生成先の tmp/are_search/sample はサンプルの受け渡し場所として使用する。
実際に編集して使うファイルと結果保存先は Rails.root/tmp の外へ置く。


# 3. 実行用ファイルを準備する
================================================================

作業用ディレクトリを用意し、2つのサンプルをコピーする。

    mkdir -p /var/lib/example/are_search/bulk/article_new_version

    cp tmp/are_search/sample/are_search_bulk_index.rb.sample /var/lib/example/are_search/bulk/article_new_version/are_search_bulk_index.rb

    cp tmp/are_search/sample/are_search_bulk_index.sh.sample /var/lib/example/are_search/bulk/article_new_version/are_search_bulk_index.sh

    chmod 700 /var/lib/example/are_search/bulk/article_new_version/are_search_bulk_index.sh

Rubyファイルとshellファイルは同じディレクトリへ置く。


# 4. Rubyファイルを設定する
================================================================

are_search_bulk_index.rb の「変更箇所」を実行対象に合わせて変更する。

対象モデルと IndexTarget。

    index_target = Article.are_search_index_target(:new_version)

使用するstage。

    sync_stage_name = "for_version_up"

bulk送信上限。

    max_bulk_bytes = 20 * 1024 * 1024
    max_bulk_count = 100
    max_fail_count = 100

max_bulk_bytes
    1回のbulk送信で使用する最大byte数。

max_bulk_count
    1回のbulk送信へ含める最大レコード数。
    max_fail_count 以下で指定する。

max_fail_count
    1回の実行中に許容する失敗件数。
    処理終了時の最後の1件は終了判定の対象外となるため、最終的な失敗件数は1件多くなる場合がある。
    1000以下で指定する。


# 5. shellファイルを設定する
================================================================

are_search_bulk_index.sh の「変更箇所」を実行環境に合わせて変更する。

Railsアプリケーションの絶対パス。

    APP_DIR="/path/to/rails_application"

結果保存先。

    RESULT_DIR="/path/to/persistent/are_search/bulk/article_new_version"

Rails環境。

    RAILS_ENV_NAME="production"

RESULT_DIR は実行単位で分ける。
別のIndexTarget、別のstage、別の作り直し処理で過去の RESULT_DIR を使い回さない。


# 6. 通常実行と再開
================================================================

shellファイルへ index を指定して実行する。

    /var/lib/example/are_search/bulk/article_new_version/are_search_bulk_index.sh index

引数を省略した場合も index として実行する。

    /var/lib/example/are_search/bulk/article_new_version/are_search_bulk_index.sh

処理が中断した場合は、同じRubyファイル、同じshellファイル、同じRESULT_DIRで再度 index を実行する。

    /var/lib/example/are_search/bulk/article_new_version/are_search_bulk_index.sh index


# 7. 失敗レコードを recover する
================================================================

通常実行で失敗したレコードを再処理する場合は、同じRESULT_DIRを使用して recover を実行する。

    /var/lib/example/are_search/bulk/article_new_version/are_search_bulk_index.sh recover

recover が完了すると、使用した結果が RESULT_DIR 直下の世代ディレクトリへ移動する。

    recover_YYYY_MM_DD_HH_MM_SS_UUUUUU/

移動しない場合は recover が完了していない。


# 8. 結果を確認する
================================================================

利用者が確認するログは RESULT_DIR 直下の bulk.log。

    /path/to/persistent/are_search/bulk/article_new_version/bulk.log

処理中も追記される。

    tail -f /path/to/persistent/are_search/bulk/article_new_version/bulk.log

RESULT_DIR には以下のディレクトリも作成される。

    data/
    recover/
    recover_YYYY_MM_DD_HH_MM_SS_UUUUUU/

data/ と recover/ は再開とrecoverで使用するため編集しない。
recover_YYYY_MM_DD_HH_MM_SS_UUUUUU/ も履歴として保持し、編集、追記、削除、移動、改名、並べ替えを行わない。
利用者の結果確認には bulk.log を使用する。


# 9. 別の投入を開始する
================================================================

別の投入処理を開始する場合は、新しい空の RESULT_DIR を指定する。
既存の data/ または recover/ だけを削除して同じRESULT_DIRを初期化しない。

対象index自体を作り直す場合も、新しいRESULT_DIRを用意して通常実行を開始する。


# 10. 巨大データを含む新IndexTargetへ切り替える
================================================================

ここでは、現在使用中のtargetを default、新しく構築するtargetを new_version、
bulk中の差分回収用stageを for_version_up、通常同期stageを default とする。


## 10-1. 新IndexTargetとbulk用stageを追加する
----------------------------------------------------------------

新しいIndexTargetと、bulk中の差分を残すstageをモデルへ追加する。

    are_search_all_sync_stage_names
        default:     ["default"]
        new_version: ["for_version_up", "default"]

    are_search_sync_stage_names_on_enqueue
        default:     ["default"]
        new_version: ["for_version_up"]

    are_search_sync_stage_names_on_after_commit
        default: ["default"]

new_version の for_version_up は enqueue するが after_commit では処理しない。
定期実行している run_sync_requests にも for_version_up を含めない。

この設定をデプロイすると、新IndexTarget用のSyncRequestが蓄積され始める。
旧IndexTargetの通常同期は継続する。

複数Webサーバがある場合は、この設定が全サーバへ反映されたことを確認してから次へ進む。


## 10-2. 新IndexTargetの空indexを作成する
----------------------------------------------------------------

AreSearch.index_operation_enabled の詳細は guide_reference.txt を参照する。

    index_target = Article.are_search_index_target(:new_version)
    result = index_target.are_search_create_index

result[:result] が :success であることを確認する。
既にaliasが存在するIndexTargetには are_search_create_index を実行できない。

bulk開始前に、対象aliasが新しく作成した空indexを指していることを確認する。

作り直す場合はbulkを停止し、対象indexを削除して作成し直す。
以前のbulk実行で使用したRESULT_DIRは再利用しない。


## 10-3. BulkIndexerを実行する
----------------------------------------------------------------

    index_target = Article.are_search_index_target(:new_version)
    sync_stage_name = "for_version_up"

実行中は通常同期用の run_sync_requests で for_version_up を処理しない。
中断した場合は同じRESULT_DIRで index を再実行する。
失敗レコードを再処理する場合は同じRESULT_DIRで recover を実行する。
進行状況と失敗内容は bulk.log で確認する。


## 10-4. bulk完了後に通常stageを追加する
----------------------------------------------------------------

BulkIndexerが完了したら、新IndexTargetへ通常同期stageの default を追加する。

複数Webサーバをローリングデプロイする場合は、最初に両stageをenqueueする中間設定を全サーバへ反映する。

    are_search_all_sync_stage_names
        default:     ["default"]
        new_version: ["for_version_up", "default"]

    are_search_sync_stage_names_on_enqueue
        default:     ["default"]
        new_version: ["for_version_up", "default"]

    are_search_sync_stage_names_on_after_commit
        default:     ["default"]
        new_version: ["default"]

全サーバへの反映後、for_version_up の新規enqueueを停止する。

    are_search_all_sync_stage_names
        default:     ["default"]
        new_version: ["for_version_up", "default"]

    are_search_sync_stage_names_on_enqueue
        default:     ["default"]
        new_version: ["default"]

    are_search_sync_stage_names_on_after_commit
        default:     ["default"]
        new_version: ["default"]

複数Webサーバがある場合は、この設定も全サーバへ反映されたことを確認してから次へ進む。


## 10-5. bulk中に蓄積した差分を回収する
----------------------------------------------------------------

for_version_up の新規SyncRequestが作成されなくなった後、run_sync_requests で回収する。

    bundle exec rake 'are_search:run_sync_requests[for_version_up]'

残っている for_version_up のSyncRequestがなくなるまで処理する。

回収完了後、new_version を通常stageだけにする。

    are_search_all_sync_stage_names
        default:     ["default"]
        new_version: ["default"]

    are_search_sync_stage_names_on_enqueue
        default:     ["default"]
        new_version: ["default"]

    are_search_sync_stage_names_on_after_commit
        default:     ["default"]
        new_version: ["default"]

この設定を全サーバへ反映する。


## 10-6. 検索入口を新IndexTargetへ切り替える
----------------------------------------------------------------

新IndexTargetのbulk投入と差分回収が完了したことを確認した後、
アプリケーションの検索入口を default から new_version へ切り替えてデプロイする。

旧IndexTargetは削除せず通常同期を継続し、問題がある場合に検索入口を戻せる状態を維持する。


## 10-7. 旧IndexTargetを停止する
----------------------------------------------------------------

新IndexTargetで問題がないことを確認した後、旧IndexTargetへの新しいSyncRequest作成を停止する。

複数Webサーバがある場合は、旧IndexTargetの定義をすぐ削除せず、
まず are_search_sync_stage_names_on_enqueue と are_search_sync_stage_names_on_after_commit の対象から外した設定を全サーバへ反映する。

旧IndexTarget用のSyncRequestが残っている場合は、定義を残したまま処理または削除方針を決める。
新しい要求が作成されない状態を確認した後、旧IndexTargetをモデル定義と検索対象から削除してデプロイする。


## 10-8. 旧Elasticsearch indexを削除する
----------------------------------------------------------------

旧IndexTargetを削除したデプロイ後もすぐにはElasticsearch indexを削除せず、アプリケーションの状態を確認する。
問題がないことを確認した後、旧IndexTargetの物理indexを削除する。


# 11. 通常同期を継続しながらBulkIndexerで全件再投入する
================================================================

ここでは、同じIndexTargetに次の3つのstageをあらかじめ定義して運用する。

    default
        通常の軽い同期。

    huge_data
        通常運用で使用する重いデータの同期。

    huge_data_for_reindex
        BulkIndexerによる全件再投入中の差分回収専用stage。

huge_data_for_reindex は保存時にSyncRequestを作成するが、
通常の run_sync_requests では処理しない。
そのため、通常運用中は huge_data_for_reindex のSyncRequestが蓄積され続ける。


## 11-1. stageを定義する
----------------------------------------------------------------

モデルには最初から3つのstageを定義しておく。

    def self.are_search_all_sync_stage_names
        {
            default: [
                "default",
                "huge_data",
                "huge_data_for_reindex",
            ],
        }
    end

    def self.are_search_sync_stage_names_on_enqueue
        {
            default: [
                "default",
                "huge_data",
                "huge_data_for_reindex",
            ],
        }
    end

    def self.are_search_sync_stage_names_on_after_commit
        {
            default: ["default"],
        }
    end

通常の rake 同期では default と huge_data だけを指定する。

    bundle exec rake 'are_search:run_sync_requests[default,huge_data]'

huge_data_for_reindex は通常の rake 同期へ追加しない。

huge_data と huge_data_for_reindex で同じ完成ドキュメントを作る場合は、
are_search_index_data から同じデータ生成処理を呼び出してよい。


## 11-2. Boundary操作用rakeを準備する
----------------------------------------------------------------

サンプルを生成する。

    bin/rails generate are_search:sample

生成される次のファイルを、利用側の rake task としてコピーして使用する。

    tmp/are_search/sample/are_search_sync_request_boundary.rake.sample

ファイル先頭の対象を変更する。

    INDEX_TARGET_MODEL_CLASS_NAME = "Article"
    INDEX_TARGET_NAME = "default"
    SYNC_STAGE_NAME = "huge_data_for_reindex"

このrakeでは次の4操作を行う。

    are_search:delete_sync_stage_all_sync_requests
        対象stageに現在溜まっているSyncRequestを削除する。

    are_search:set_sync_request_boundary
        bulk完了時点のrequest sequenceを境界として保存する。

    are_search:run_sync_request_before_boundary
        保存した境界までのSyncRequestだけを同期する。

    are_search:clear_sync_request_boundary
        差分回収完了後に保存した境界を削除する。


## 11-3. bulk開始前のSyncRequestを削除する
----------------------------------------------------------------

bulk開始直前に、通常運用中に蓄積していた
huge_data_for_reindex のSyncRequestを削除する。

    bundle exec rake are_search:delete_sync_stage_all_sync_requests

削除後も huge_data_for_reindex のSyncRequest作成は停止しない。
この時点以降に発生した更新は再び蓄積される。


## 11-4. BulkIndexerを実行する
----------------------------------------------------------------

BulkIndexerでは huge_data_for_reindex を使用する。

    index_target = Article.are_search_index_target(:default)
    sync_stage_name = "huge_data_for_reindex"

通常どおりbulkを実行する。

    /path/to/are_search_bulk_index.sh index

中断した場合は同じRESULT_DIRで再開する。
失敗レコードがある場合は必要に応じてrecoverする。

    /path/to/are_search_bulk_index.sh recover

bulkと必要なrecoverが完了するまで、
次のBoundaryTarget設定は行わない。


## 11-5. bulk完了時点を境界として保存する
----------------------------------------------------------------

bulkと必要なrecoverが完了したら BoundaryTarget を設定する。

    bundle exec rake are_search:set_sync_request_boundary

この操作で、その時点のrequest sequenceが境界として保存される。

以降に作成される新しいSyncRequestは通常運用分として蓄積を続け、
今回の差分回収対象には含めない。


## 11-6. bulk中の差分を同期する
----------------------------------------------------------------

専用rakeを実行する。

    bundle exec rake are_search:run_sync_request_before_boundary

実行時には、今回の境界までに発生したSyncRequestの件数が表示される。

対象が存在する場合は実行確認が表示される。

    同期を実行しますか？ [y/N]:

y を入力すると同期を開始する。

実行後にも残件数が表示される。

残件がある場合は、同じコマンドを再度実行する。

    bundle exec rake are_search:run_sync_request_before_boundary

BoundaryTarget 以前のDBの更新は全て対象となる
コミットが遅れているデータがあとから増える可能性があるが、後から増えた
データは本来であれば処理の対象外だが、安全側に倒して処理をしているだけ。
そのため、一度でも実行前の対象件数が0件になれば問題ない。

    [AreSearch] Boundary同期対象 実行前 0件

0件になれば、今回のbulk中に蓄積した差分回収は確認完了。


## 11-7. 差分回収後に境界を削除する
----------------------------------------------------------------

run_sync_request_before_boundary の実行前対象件数が0件になったら、
今回保存したBoundaryTargetを削除する。

    bundle exec rake are_search:clear_sync_request_boundary

次回の set_sync_request_boundary は、新しいBoundaryTargetを作成する。


## 11-8. 次回のbulk
----------------------------------------------------------------

次回も同じ手順を繰り返す。

    1. are_search:delete_sync_stage_all_sync_requests
    2. BulkIndexerを実行し、必要ならrecover
    3. are_search:set_sync_request_boundary
    4. are_search:run_sync_request_before_boundary を0件になるまで実行
    5. are_search:clear_sync_request_boundary

huge_data_for_reindex は通常の run_sync_requests では処理しないため、
次回bulkまでの間もSyncRequestは蓄積され続ける。

## 11-9. Boundary操作で回収する範囲
----------------------------------------------------------------

4つの操作とbulkの位置関係は次のようになる。

    delete_sync_stage_all_sync_requests
        |
        |  データA: 更新 → commit
        |
        |  データB: 更新 --------------------→ commit
        |
        |  BulkIndexer
        |      開始
        |      ...
        |      終了
        |
    set_sync_request_boundary
        |
        |  データC: 更新 → commit
        |
    run_sync_request_before_boundary
        |
        |  対象が0件になるまで繰り返す
        |
    clear_sync_request_boundary


delete_sync_stage_all_sync_requests
    それ以前に蓄積されていた huge_data_for_reindex のSyncRequestを削除する。
    今回のbulkで回収する範囲の開始点になる。

データA
    delete_sync_stage_all_sync_requests後に更新され、set_sync_request_boundaryより前にcommitまで完了している。

データB
    set_sync_request_boundaryより前に更新処理が始まっているが、commitが境界設定付近まで遅れている。
    transactionの長さなどによりコミットが境界の前後のどちらを安全に判定できない。

set_sync_request_boundary
    この時点で今回の差分回収の終了境界を設定する。
    以後の通常更新を、今回のbulk差分から分けるために使用する。

データC
    set_sync_request_boundary後に更新され、commitされた通常の更新。

専用rakeは、set_sync_request_boundaryまでにコミットされたデータだけを同期対象にしたい。
しかし、明確にはわからないためデータAだけでなくデータBも拾う。
データCは確定しているため対象外。

また、データAやBにその後さらに更新が入り、SyncRequestがset_sync_request_boundaryより後の
新しい要求へ更新された場合は、最新の通常更新として扱う。
今回の境界へ固定して処理する必要はない。

run_sync_request_before_boundary は、この境界までにbulkへ反映できなかった可能性がある
SyncRequestだけを処理する。
実行前の対象件数が0件になれば、今回のbulk差分回収は完了となる。
clear_sync_request_boundary は、差分回収に使用したBoundaryTargetを削除する。
