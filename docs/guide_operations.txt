================================================================
AreSearch 運用ガイド
================================================================

このガイドは、index の状態確認、reindex、clean up、SyncRequest の回収、sync lock、障害対応を扱う。
導入は guide_setup.txt、IndexTarget と sync stage は guide_index_targets_and_stages.txt、
設定と低レベルAPIは guide_reference.txt を参照する。


# 1. index の準備状態を確認する
================================================================

検索前やメンテナンス判定で、対象 index の alias が存在するか確認する。

    ready = AreSearch::Searcher.index_ready?(
        [
            Article.are_search_index_target(:default),
            Comment.are_search_index_target(:default),
        ]
    )

alias が存在しない、または状態確認に失敗した場合は false を返す。
sync lock は判定対象にしない。
検索を止める必要がある場合のメンテナンス表示はアプリ側で行う。


# 2. reindex
================================================================

先頭stageでreindexする。

    result = Article
        .are_search_index_target(:default)
        .are_search_reindex(stage_position: :first)

末尾stageでreindexする。

    result = Article
        .are_search_index_target(:default)
        .are_search_reindex(stage_position: :last)

Searchable を継承した子クラスからは実行せず、継承系統の最上位モデルの IndexTarget で実行する。

実行後は result[:result] が :success であることを確認する。
失敗した場合は返された診断情報を確認し、必要に応じて are_search:check_index_status で index の状態を確認する。
戻り値の各項目は guide_reference.txt の「index 操作の戻り値」を参照する。
reindex 中の検索は切り替え前の alias を使用する。
失敗時に作成された物理 index が残った場合は、原因確認後に clean up または手動削除する。

mappings、analyzer、index_settings の変更を反映するには reindex が必要。
AreSearch.batch_size の詳細は guide_reference.txt を参照する。


## 2-1. Elasticsearch バージョンアップ前の全 reindex
----------------------------------------------------------------

    bundle exec rake are_search:reindex_all_for_es_version_up

以下に問題がある場合は開始しない。

    are_search_sync_requests に未処理レコードが残っている
    AreSearch.index_prefix 配下に alias 未接続の index がある

対象 index を確認し、y または Y を入力した場合だけ順番に reindex する。
各IndexTargetの末尾stageを使用する。


# 3. clean up
================================================================

alias が指していない古い物理 index を削除する。

単一target。

    result = Article
        .are_search_index_target(:default)
        .are_search_clean_up

実行後は result[:result] が :success であることを確認する。
失敗した場合は are_search:check_index_status で alias、sync lock、物理 index の状態を確認する。

全target。

    bundle exec rake are_search:clean_up_all

現在 alias が指している物理 index は削除しない。


# 4. index 状態を確認する
================================================================

    bundle exec rake are_search:check_index_status

各 index target の alias、物理 index、sync lock、index lock などの状態と警告を表示する。
sync lock を強制解除する場合にも、このタスクで状態を確認する。

このタスクは、AreSearch で作成された index を対象とする。


# 5. manual sync lock
================================================================

計画メンテナンス中に、新しい同期処理やindex操作を開始させない場合に使用する。
検索は自動停止しない。

全targetの index target sync lock を操作する。

    bundle exec rake are_search:acquire_sync_lock_all
    bundle exec rake are_search:release_sync_lock_all

単一target全体を操作する。

    index_target = Article.are_search_index_target(:default)

    index_target.are_search_acquire_sync_lock!
    index_target.are_search_release_sync_lock!

特定stageだけを操作する。

    sync_stage_name = "with_external_file"

    index_target.are_search_acquire_sync_stage_lock!(sync_stage_name)
    index_target.are_search_release_sync_stage_lock!(sync_stage_name)

通常解除は manual sync lock だけを削除する。
異常終了で残った別operationの sync lock は「sync lock を手動解除する」の手順で確認してから解除する。
これらの操作には AreSearch.index_operation_enabled = true が必要。


# 6. SyncRequest を定期回収する
================================================================

SampleGenerator で生成した rake task のサンプルを利用側アプリケーションへコピーする。

    cp tmp/are_search/sample/are_search_run_sync_requests.rake.sample \
        lib/tasks/are_search_run_sync_requests.rake

    cp tmp/are_search/sample/are_search_sync_limit_alert.rake.sample \
        lib/tasks/are_search_sync_limit_alert.rake

コピーした rake ファイルは運用に合わせて内容を確認・編集する。

are_search_run_sync_requests.rake では、通常同期とforce同期の対象scopeを利用側の運用に合わせて変更できる。
標準の対象条件をそのまま使用する場合は変更不要。

force同期は、別の処理が processing_token を保持したまま一定時間停止した SyncRequest を補助的に再反映する処理。
processing_at が sync_request_process_hang_wait より古く、force_try_count が max_force_try_count 未満の要求が候補になる。
通常同期と異なり、force同期は Elasticsearch への反映だけを行い、sync_try_count と同期後callbackは進めない。
実行すると force_attempted、last_force_try_at、force_try_count が更新される。
残った processing_token を手動解除する必要がある場合は「processing_token を手動解除する」を参照する。

are_search_sync_limit_alert.rake は実行前に、通知先・送信元と通知閾値を環境に合わせて変更する。

    ALERT_MAIL_TO
    ALERT_MAIL_FROM
    ALERT_SYNC_TRY_THRESHOLD
    ALERT_FORCE_TRY_THRESHOLD
    ALERT_STUCK_ERROR_WAIT

メール送信には利用側Railsアプリケーションの config.action_mailer の設定を使用する。

タスクを実行する環境では AreSearch.rake_operation_enabled を有効にする。
設定の詳細は guide_reference.txt を参照する。

単一stageを回収する。

    bundle exec rake 'are_search:run_sync_requests[default]'

複数stageを回収する。

    bundle exec rake 'are_search:run_sync_requests[default,with_external_file]'

回収条件、試行上限、rake_operation_enabled の詳細は guide_reference.txt を参照する。
SyncRequest の状態項目は guide_reference.txt の「SyncRequest の状態項目」を参照する。

重いstageを別時間帯に処理する場合は、stageごとに定期実行を分ける。

現在残っている sync request、sync lock を確認する。

    bundle exec rake are_search:check_sync_request_status

主な表示内容。

    現在存在する sync lock
    sync request の件数とエラー状況

通知用タスク。

    bundle exec rake are_search:sync_limit_alert


# 7. SyncRequest Boundary
================================================================

BulkIndexer 実行中の差分回収など、特定の時点までに発生した SyncRequest だけを後から同期する場合に使用する。
SampleGenerator で生成した専用 rake task のサンプルを利用側アプリケーションへコピーする。

    cp tmp/are_search/sample/are_search_sync_request_boundary.rake.sample \
        lib/tasks/are_search_sync_request_boundary.rake

コピーした rake ファイルで対象を指定する。

    INDEX_TARGET_MODEL_CLASS_NAME = "Article"
    INDEX_TARGET_NAME = "default"
    SYNC_STAGE_NAME = "huge_data_for_reindex"

タスクを実行する環境では AreSearch.rake_operation_enabled を有効にする。


## 7-1. bulk開始前のSyncRequestを削除する
----------------------------------------------------------------

対象stageに現在溜まっているSyncRequestを削除する。

    bundle exec rake are_search:delete_sync_stage_all_sync_requests

削除後に作成されたSyncRequestは再び蓄積される。


## 7-2. bulk完了時点を境界として保存する
----------------------------------------------------------------

bulkと必要なrecoverが完了した後に実行する。

    bundle exec rake are_search:set_sync_request_boundary

実行時点のrequest sequenceをBoundaryTargetへ保存する。


## 7-3. 境界までのSyncRequestを同期する
----------------------------------------------------------------

    bundle exec rake are_search:run_sync_request_before_boundary

保存した境界以前に作成されたSyncRequestを同期対象にする。
コミット時期は問わないため多めに拾う可能性がある。
実行前に対象件数を表示し、対象が存在する場合は確認後に同期する。

    同期を実行しますか？ [y/N]:

実行後にも対象件数を表示する。
実行前の対象件数が0件になるまで同じコマンドを繰り返す。


## 7-4. 差分回収後に境界を削除する
----------------------------------------------------------------

対象件数が0件になった後、今回保存したBoundaryTargetを削除する。

    bundle exec rake are_search:clear_sync_request_boundary

Boundary操作をBulkIndexerと組み合わせる具体的な手順は guide_bulk_indexer.txt を参照する。


# 8. モデル設定を確認する
================================================================

    bundle exec rake are_search:check_all_models

正常な場合。

    全モデル正常

デプロイ後や mappings / stage 定義を変更した後の確認に使用する。


# 9. コールバックを通らないDB更新
================================================================

update_columns、update_all、delete_all、insert_all、upsert_all、SQL直接実行は ActiveRecord コールバックを通らない。
通常saveと同じ同期経路へ乗せる方法と、Elasticsearchへ直接反映する低レベルAPIは guide_reference.txt を参照する。

件数が多い場合は reindex を使用する。

    index_target.are_search_reindex(stage_position: :first)


# 10. 障害時の確認順序
================================================================


## 10-1. 検索結果が古い
----------------------------------------------------------------

    1. are_search_sync_requests にレコードが残っているか確認する
    2. after_commit_mode = :job の場合は Job worker を確認する
    3. 対象stageを指定して run_sync_requests を実行する
    4. last_error、sync_try_count、callback_try_count を確認する


## 10-2. reindex または sync が動かない
----------------------------------------------------------------

    1. bundle exec rake are_search:check_index_status を実行する
    2. sync lock、index lock の状態を確認する
    3. alias と物理 index の状態を確認する


## 10-3. 古い物理 index が増えている
----------------------------------------------------------------

    Article.are_search_index_target(:default).are_search_clean_up


# 11. sync lock
================================================================


## 11-1. block形式でsync stage sync lockを使う
----------------------------------------------------------------

処理中だけ特定stageで新しい同期処理を開始させない場合は are_search_with_sync_stage_lock を使用する。
AreSearch.index_operation_enabled = true が必要。

    index_target = Article.are_search_index_target(:default)

    index_target.are_search_with_sync_stage_lock(
        "with_external_file",
        operation: "bulk",
    ) do
        Article.find_each do |article|
            article.are_search_index_or_delete!(
                index_target,
                "with_external_file",
            )
        end
    end

sync stage sync lock は、指定stageで新しい同期処理を開始させない。
lock取得前にprocessingへ入ったSyncRequestはそのまま処理を継続する。
既存processingと競合させられない処理では、利用側で終了を確認してから処理を開始する。


## 11-2. sync lock を手動解除する
----------------------------------------------------------------

異常終了で sync lock が残った場合は、先に check_index_status または check_sync_request_status で状態を確認する。
実行中の処理がないことを確認してから強制解除する。

    index_target = Article.are_search_index_target(:default)
    sync_stage_name = "with_external_file"

IndexTarget全体の sync lock を強制解除する。

    index_target.are_search_force_release_sync_lock!

特定stageの sync lock を強制解除する。

    index_target.are_search_force_release_sync_stage_lock!(sync_stage_name)

強制解除は operation や所有者に関係なく対象lockを削除する。
実行中の処理がある状態では使用しない。
AreSearch.index_operation_enabled = true のプロセスでのみ実行する。


# 12. 物理 index を手動削除する
================================================================

物理 index 名を確認する。

    index_pattern = AreSearch.join_index_name(
        AreSearch.index_prefix,
        "*",
    )

    AreSearch.client.indices.get(index: index_pattern)

現在使用中の物理 index を誤って削除しないよう、事前に alias を確認する。
手動削除APIの詳細は guide_reference.txt を参照する。


# 13. processing_token を手動解除する
================================================================

run_sync_requests の強制同期後も processing_token が残り続ける場合の最終手段。
Job が再開しないことを確認してから行う。

対象を確認する。

    sync_request = AreSearch::SyncRequest.find(id)

解除条件。

    sync_request.processing_token が存在する
    sync_request.force_attempted が true
    sync_request.force_try_count が 1 以上
    processing_at が十分古い
    対象 Job が存在しない、または Job worker を停止済み

解除する。

    updated_count = AreSearch::SyncRequest
        .where(id: sync_request.id)
        .where(force_attempted: true)
        .where("force_try_count > 0")
        .update_all(
            processing_token: nil,
            processing_at:    nil,
        )

    puts updated_count

updated_count が1なら通常同期へ戻す。

    bundle exec rake 'are_search:run_sync_requests[default]'

対象の sync_stage_name に合わせて引数を変更する。
